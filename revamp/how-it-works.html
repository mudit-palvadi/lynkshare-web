How it works

One file, two devices, no account.

LynkShare is a cross-device file transfer service. It works between a phone and a laptop, two laptops, two phones, or a tablet and a computer. The sender can use the Android app or the web sender; the receiver can open a link in a browser or use the Android app.

There is no iOS app. On iPhone and iPad, LynkShare works through the browser receiver in Safari or Chrome, with the 10 MB web limit.

Cloud or Direct

The sender chooses how the file should travel. The right choice depends on whether both people are online at the same time and how much of the transfer path should be handled by LynkShare.

CloudDirect
The encrypted file is stored temporarily so the recipient can open the link later during the session. The two devices connect to each other and the file is streamed over the direct channel.
Best when the recipient is not ready yet, or when a direct connection is blocked. Best when both people are online and want the shortest path without a stored file copy.
The web limit applies: 10 MB total per transfer. The app supports the larger Direct limit; the web remains at 10 MB.
The service stores ciphertext and session metadata until expiry or cleanup. If the connection fails, LynkShare can continue with the encrypted Cloud copy.

Sender QR and Receiver QR

The two QR directions are the main LynkShare experience. They answer a simple question: who is holding the device that needs to be scanned?

Sender QR

The sender picks the files, chooses Cloud or Direct, and shows a QR code or shares the link. The receiver scans the sender's QR or opens the link. This is the usual flow when the sender starts the transfer. The link can also be sent remotely, so the receiver does not have to be in the same room.

Receiver QR

The receiver opens the receiving screen and shows a QR code. The sender scans that QR from the Android app, which tells LynkShare which device is waiting. The sender then sends the file to that device. This is the in-person flow for “send to this phone or laptop.” The receiving-QR path uses Cloud delivery.

Use Sender QR when the sender is starting the transfer or the link needs to be shared remotely. Use Receiver QR when the receiver is already waiting and the sender can scan the screen in front of them.

Encryption and the link key

Files are encrypted on the sender's device before they leave it. The file key is generated on the device and stays in the link fragment. Browsers do not send the fragment to the server, and LynkShare does not store it. The server receives ciphertext, not plaintext.

A share link is a capability: anyone who has the complete link can attempt to open the transfer. Treat a complete link, QR image, or code as sensitive. The service does not receive the file key, but it does process metadata.

What the server stores

  • File names, sizes and content types for the session.
  • Transfer and receiver-session identifiers and status.
  • Network addresses used to make the service work and limit abuse.
  • Encrypted file bytes when Cloud delivery is used.

Session metadata expires with the transfer, normally within 10 to 30 minutes. Encrypted Cloud objects are deleted by the bucket lifecycle within 24 hours, and cancelling a transfer removes its objects immediately. Local history stays on the device and can be cleared.

Limits and expiry

The web sender allows up to 10 MB total per transfer, with at most 10 files. The Android app allows 15 MB Cloud and 20 MB Direct on the standard tier, and 30 MB Cloud and 50 MB Direct after the in-app unlock. The service ceiling is 50 MB per transfer.

A transfer normally lasts 10 minutes. The Android app can extend the session to 30 minutes when the sender secret is available. A reload needs the original link because the key is not stored by the site.

Privacy limits

  • Encryption does not make the service anonymous.
  • Direct connections can expose network addresses to the other peer and the connection service.
  • A TURN relay can observe connection metadata, not plaintext file contents.
  • Cloud storage keeps encrypted objects for the cleanup window, even after the download session ends.

For private vulnerability reporting, use the LynkShare security policy.
